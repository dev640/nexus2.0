# Multi-tenancy schema notes

Phase 1 of the multi-tenancy rollout (migrations V18–V21) puts every piece of
tenant data under exactly one company. This page records the decisions that
are not obvious from the migrations themselves, and the **explicit exceptions**
the Phase 4 ArchUnit / integration tests must allow.

## Model

- `companies` (V18) is the tenant. Every tenant table carries
  `company_id BIGINT NOT NULL REFERENCES companies(id)` with an index on it.
- `users.company_id` is nullable **only** for `SUPER_ADMIN`, which belongs to
  no company. Two named CHECKs on `users` enforce the role vocabulary and the
  rule that a non-SUPER_ADMIN must have a company (V18).
- `(company_id, id)` is unique on every tenant table and on `users` (V19).
  Every foreign key between two tenant tables has a **composite twin**
  `(company_id, fk) -> parent(company_id, id)` so a child row can never point
  across companies. The original single-column foreign keys remain in place:
  they own the `ON DELETE` behaviour (CASCADE / SET NULL); the twins use the
  default `NO ACTION / MATCH SIMPLE` and only police the company pairing.
- Employee codes (`NX-0007`) are unique **per company**, not globally, and are
  generated by the application per company (`companies.employee_seq`). The old
  global `user_employee_code_seq` object is left in place but unreferenced.
- `users.email` remains globally unique; `ux_users_email_lower` additionally
  enforces case-insensitive uniqueness so `Devendra@nexus.com` cannot shadow
  `devendra@nexus.com`.
- `audit_log` (V20) records admin/security actions. It intentionally has **no**
  FK on `actor_user_id`: audit rows must survive user deletion.

## Explicit exceptions (Phase 4 ArchUnit allowlist)

1. **`task_labels`** — an `@ElementCollection` join table with no entity and no
   `company_id` of its own. Reachable only through its tenant-scoped parent
   (`tasks`). No composite twin is possible; integrity comes from the parent.
2. **`knowledge_chunks.owner_id`** — the knowledge index is a derived table
   with no foreign keys by design (kept in sync by the application). V19 adds
   only an index `(company_id, owner_id)`; the application (and test B10)
   enforces that an owner belongs to the chunk's company.
3. **`password_reset_requests.resolved_by`** — keeps its single-column FK only.
   The resolver may be a `SUPER_ADMIN` with `company_id IS NULL`, which a
   composite twin would reject.
4. **`UserRepository.findByEmail` / `findBySupabaseId` / `findFirstByEmailIgnoreCase`,
   and `CustomUserDetailsService`** (login path) — resolve accounts across all
   companies, because a person signing in has not yet said which company they
   belong to. Every other user query takes a company. `ux_users_email_lower`
   means one address cannot exist twice, so "which company is this email in" is
   not a question the login has to answer.
5. **String author columns** (`whiteboard_notes.author`,
   `wiki_pages.author`, `chat_channels.created_by`) — free-text names, not
   user ids; they have no FK today and gain none.
6. **`Company`** (entity) — it *is* the tenant. It has no `company_id`; every
   other table's `company_id` points at its `id`.
7. **`AuditLog`** (entity) — a global action by a `SUPER_ADMIN` belongs to no
   company, so the row is written with an explicit, nullable `company_id`
   instead of being stamped. A tenant stamp would refuse to write exactly the
   actions that most need recording. Its `actor_user_id` has no FK either: the
   record must survive the deletion of the account it names.
8. **`PasswordResetRequest` filed from a public endpoint** — the request path is
   unauthenticated, so there is no tenant in scope; the company is taken
   explicitly from the account the request is *for*.
9. **`KnowledgeChunk` writes during a reconcile** — a reindex walks every
   company's source records in one pass, so the chunk's company comes from its
   source record (`SourceDocument.companyId()`), never from the ambient tenant.
   A chunk that took its company from the caller would be filed under the wrong
   one, silently.

## Phase 2: what the application layer enforces today

Schema (phase 1) made cross-company rows impossible to *insert*. Phase 2 makes
the application agree with it. Landed:

- **`TenantAware` + `TenantStampListener`** — every tenant entity, except the
  exceptions above, carries a `company_id` and is stamped from `TenantContext`
  on insert. An explicitly assigned company always wins (see exceptions 7–9); a
  row with neither is refused rather than written with a guessed company.
- **`TenantContext` / `TenantScope` / `CurrentTenant`** — the company of the
  current unit of work. `TenantScope` carries it across a thread boundary (the
  streamed AI answer persists its turns on a pool thread); `CurrentTenant.require()`
  answers a `SUPER_ADMIN` with 403 rather than an unscoped listing.
- **`JwtAuthenticationFilter`** is the only place the tenant is established. It
  reads the company from the account row (via `NexusUserPrincipal`), not from a
  token claim, so a company or role change takes effect on the next request
  rather than at token expiry — and it clears the thread in a `finally`, which is
  what stops Tomcat reusing a pooled thread with the previous request's company.
- **Per-company employee codes** — `EmployeeCodeService` allocates from
  `companies.employee_seq` under a row lock. The old global sequence is gone
  (V19), so one company's numbering no longer leaks its headcount to another.
- **`audit_log`** — written by `AuditService` for account creation, deletion,
  role changes and the password-reset lifecycle. Callers supply only what
  happened; actor, company and IP are read from the request. A failure to write
  the row fails the action: V20's rule is that an auditable action has a record.
- **Scoped reads** for accounts, password resets, the chat mention audience, the
  activity-notification audience, message broadcasts, the knowledge index and
  retrieval (both the SQL search and the in-memory vector filter).
- **Self-provisioning removed** — a valid Supabase identity with no local
  account is refused (401) instead of being given an account. An account needs a
  company and a code, and choosing a company for a stranger is the one thing
  tenancy exists to prevent. An admin creates the account; the Supabase sign-in
  then links to it.
- **`EntitySchemaConformanceTest`** boots the application against a
  migration-built database, so `ddl-auto=validate` proves the model matches
  V18–V21, and pins that every entity is either `TenantAware` or on the
  exception list above.

### Scope audit (phase 2 complete)

Every resource service now resolves its rows through a company-predicated
lookup — projects, sprints, tasks, wiki, whiteboard, chat channels/messages,
avatars, push subscriptions, mail and notifications all use
`findByIdAndCompanyId` / `findByCompanyId` / `existsByIdAndCompanyId` (or an
ownership check that is stricter, as with per-user mail and notifications).
Two reads are deliberately *not* company-predicated and are checked instead by
ownership: `MessageService` and `NotificationService` load by id and then
refuse unless the caller is the sender or recipient — a message or notification
belongs to named people, and the ownership check cannot be satisfied across
companies because the email comparison can only match the caller's own account.

The knowledge reconcile is scoped at both of its locks: `SourceDocuments.all(companyId)`
feeds only the caller's company's records (never a full-table scan filtered in
memory), and `KnowledgeIndexService.reindex` re-filters the feed defensively so
a mis-scoped query still cannot index another company's content
(`KnowledgeIndexServiceTest`).

### Still open (phase 3)

- ~~SUPER_ADMIN cross-company tooling does not exist~~ — **done**:
  `SuperAdminService` + `SuperAdminController` (`/api/admin/companies`,
  `/api/admin/accounts`, and the suspend/resume routes) give a deliberate
  cross-company view. They never reuse a tenant-scoped method: the listings take
  no ambient tenant and are the only place a cross-company read is allowed,
  reachable solely from a `hasRole('SUPER_ADMIN')` endpoint. That is the exact
  shape the note below called for — the safe 403 default for every workspace read
  stays untouched, and the operator who must see across workspaces gets their own
  route (`SuperAdminSecurityTest` pins that an ordinary ADMIN is refused every
  one of them).
- **Creating a second company — done.** `POST /api/admin/companies` is
  SUPER_ADMIN-only and creates the company, its first ADMIN, and the
  `COMPANY_CREATED` audit row in one database transaction. The response is
  `201 Created`, points `Location` at the company collection, and is
  `Cache-Control: no-store` because it contains the generated initial password.
  The password is returned once, is never written to the audit metadata, and
  `must_change_password` forces the new admin to rotate it at first sign-in.
  Company names are checked case-insensitively before insert and the unique
  index race is translated to a validation response. Duplicate admin emails
  return a generic `409` for both local accounts and Supabase `email_exists`
  conflicts; the response does not identify the existing tenant.

  The schema confirms `audit_log.company_id` is nullable and
  `actor_user_id` has no foreign key, so global operator actions remain
  attributable without requiring a tenant and survive actor deletion. A
  Supabase identity is created before the database transaction can commit; if
  the transaction rolls back, an after-rollback callback attempts to delete
  that identity. Cleanup failure is logged at error level without the remote
  error text or secrets; it cannot be made atomic with PostgreSQL.

  `TwoCompanyIsolationTest` creates both companies through the real HTTP
  endpoint and verifies tenant-scoped listings, cross-company `404` behavior,
  direct-message privacy, SUPER_ADMIN listings and the ADMIN denial. The
  production deployment gate below still applies before this endpoint is used
  against production data.

## Forced password change (enforced)

`must_change_password` is set wherever an admin chooses the password — account
creation with a generated password, and a resolved reset request — and is now
enforced end to end rather than only recorded:

- **`NexusUserPrincipal`** reads the flag from the account row on every request.
  It is deliberately not a token claim: the flag is cleared by the change itself,
  so it has to be current, and a stale claim must never be able to open the gate.
- **`MustChangePasswordFilter`** (wired in `SecurityConfig` directly after the
  JWT filter) refuses every request from a gated account with
  `403 {"code":"PASSWORD_CHANGE_REQUIRED"}`. Exactly two requests pass:
  `POST /api/users/me/password` and `GET /api/users/me`, plus CORS preflights.
  It is instantiated in the config rather than annotated `@Component`, because a
  filter bean is also registered on the servlet container's chain where it would
  run before authentication and do nothing.
- **`MustChangePasswordHandshakeGuard`** applies the same rule to the chat and
  whiteboard socket handshakes. The filter cannot: a browser opens a socket
  without an `Authorization` header, the token travels as a query parameter and
  is read by the handshake interceptor, so nothing is in scope in the security
  context. Without this the gate would have refused every HTTP call and left the
  message stream wide open on the same account.
- **`POST /api/users/me/password`** (`PasswordChangeService`) requires the
  current password, refuses reuse of it, writes to whichever store owns the
  credential — the local bcrypt hash, or the Supabase Auth Admin API for a
  Supabase-linked account — clears the flag in the same transaction, and records
  `PASSWORD_CHANGED` without recording anything derived from the password.
  Open to every role including VIEWER: the accounts most likely to hold an
  admin-issued password are those with the least access, and one that cannot
  rotate its own password is stuck on a password an admin knows.
- **The client** renders the forced-change screen in place of the workspace
  (`App.tsx`), driven by the flag on the profile, and `lib/api.ts` reacts to the
  marker so a stale client recovers instead of seeing every request fail.

Known limitation: for a local account, access tokens issued before the change
remain valid until they expire — they are stateless JWTs, and there is nothing to
invalidate them against. Closing that needs a password-changed timestamp or token
version on the account, checked per request. A Supabase-linked account has no
such window: Supabase ends that account's sessions when its password changes.

## Company suspension (enforced)

`companies.status` was already `ACTIVE`/`SUSPENDED` in the schema (V18) but
nothing read it: a suspended company's people could sign in and work as if
nothing had happened. It is now a hard lockout, read from the row on every
request and socket the same way `must_change_password` is — never from a token
claim, so an operator suspending a workspace takes effect on its people's very
next request rather than at token expiry.

- **`NexusUserPrincipal`** carries `companySuspended`, read from the company row
  (fetched with the account by `findByEmailWithCompany`) on every request.
- **`SuspendedCompanyFilter`** (wired in `SecurityConfig` after the password
  gate) refuses every request from a suspended company with
  `403 {"code":"WORKSPACE_SUSPENDED"}`. Exactly one read passes — `GET
  /api/users/me` — so the client can tell a suspended session from a dead one and
  render the screen that says who can lift it; that read grants no workspace
  data. CORS preflights pass so a sign-out is not reported as a network failure.
- **`UserService.login` / `.refresh`** refuse a suspended company at the door.
  These two endpoints run before any authentication exists, so there is no
  principal for the filter to gate; they check the row themselves. A wrong
  password is still reported as such even for a suspended company, so the door
  does not disclose the suspension to someone who never got in.
- **`SocketPrincipalResolver`** refuses a socket handshake for a suspended
  company, on both the chat and whiteboard connections — a browser opens a socket
  with a token in the query and no principal in scope, so the HTTP filter never
  sees it and the rule has to be applied where the token is read.
- **`CompanySuspensionService.suspend`** sets the row, writes a
  `COMPANY_SUSPENDED` audit row in the same transaction, and ends the company's
  live sockets via `CompanySocketCloser` (both the chat and the whiteboard
  registry). Because that close is local to the instance that handled the
  request, the same suspension is published on a Redis control channel
  (`nexus:company:suspension`); `CompanySuspensionConfig` subscribes and closes
  the company's sockets on every other instance. Redis is optional — with none,
  a single-instance deployment needs no cross-instance control, and the handshake
  still refuses new connections everywhere because every instance reads the same
  row.
- **`POST /api/admin/companies/{id}/suspend|resume`** (`CompanyAdminController`)
  is SUPER_ADMIN-only and deliberately *not* tenant-scoped: a suspension targets
  a company by id and locks its people out of every session, which is exactly the
  kind of cross-company action the runbook says needs its own endpoint rather
  than a tenant-scoped service method (which would refuse a SUPER_ADMIN, who has
  no company).

Enforcement does not depend on that endpoint: the filter, the login/refresh
checks and the handshake all read the company row, so flipping it by any means
locks the workspace out everywhere on the next request.

## Deployment gate (before any production deploy)

Nothing from this rollout ships to production until all three hold:

1. The four V2 seed accounts (known password `password123`) are changed or
   deleted.
2. Verified on the real database: no `@supabase.local` users exist, and every
   `role` value is one of `ADMIN, MEMBER, VIEWER, DEVELOPER, MANAGER,
   SUPER_ADMIN`.
3. A `pg_dump` backup exists and V18–V21 have been dry-run against a restored
   copy of it.
4. ~~Every read path listed above is company-scoped~~ — **done**: all read
   paths are company-scoped or ownership-checked (see "Scope audit"), pinned by
   `KnowledgeIndexServiceTest`, `EntitySchemaConformanceTest` and the per-service
   tests. A second company exists only after that, and only alongside the
   SUPER_ADMIN tooling above.

## Rollback

Reverse scripts live in `docs/rollback/`, one per migration. Apply them in
reverse order: V21 → V20 → V19 → V18. V21's reverse recreates structure only —
the V2 seed row and any organization_id values come back only from a pg_dump
backup. The reverses restore the V17 *shape*, never the data they discarded.
